# Project Zomboid服务器怎么开：要多少内存、开哪些端口、模组和备份怎么处理？（附10人与100人服端口对照表）

开一个 Project Zomboid 专用服，要先解决三件很具体的事：16261 之后那一长串 UDP 端口怎么放行、JVM 内存上限给到多少、关服和备份怎么处理。这三件决定你该买什么机器，也决定存档能不能活过第一次模组更新。10 人以内的小服按 8G 内存和 10 个客户端槽位起步；30 人以上或者挂着两三百个模组的服，端口段和内存都得重新算。

## 端口是第一道门槛：每个玩家占一个 UDP 端口

PZ 服务端要放行的端口不止一个 16261。游戏主端口是 16261/udp，Steam 用 8766/udp 和 8767/udp，RCON 远程控制台是 27015，而客户端槽位从 16262 开始，**每个玩家占一个**。

| 用途 | 端口 | 协议 | 说明 |
| --- | --- | --- | --- |
| 游戏主端口 | 16261 | UDP | 玩家连接入口，对外必须可达 |
| 客户端槽位 | 16262 起 | UDP | 每玩家一个，必须连续 |
| Steam 端口 | 8766、8767 | UDP | 服务端与 Steam 通信 |
| RCON | 27015 | TCP | 远程控制台与自动关服 |

人数直接决定端口段长度。常见的容器化开服方案里，`PLAYER_PORTS` 的默认值就是 16262-16272，对应 10 个槽位；100 个槽位则要放到 16262-16362。按每玩家一个端口算，30 人的服要到 16292。

这一段连续 UDP 端口，会淘汰掉一批便宜机器。走 NAT 端口映射的实例，每条规则只能填一个外部端口、一个内部端口和一个协议，10 人服就是十几条规则要手动加，人一多基本没法维护。雨云的开服教程里把实例分成公网 IP 和 NAT 端口映射两类，前者直接用公网 IP 访问，后者要在控制台逐条添加映射。开 PZ 服选后者不是不能跑，是端口段一长，配置成本会盖过省下的那点钱。

## 内存给多少：8G 是默认值，也是很多人的天花板

主流的一键开服方案里，`PZ_MEMORY_LIMIT` 默认就是 8g，`PZ_MAX_PLAYERS` 默认是 8。也就是说默认配置只保证 8 个人、少量模组能跑。

模组加量就得往上调 JVM 上限。但这里有个容易忽略的第二层限制：容器和虚拟机自己还有一道内存天花板，JVM 参数改不动它。在 Windows 上跑 Docker，内存上限由 WSL 2 决定；你写 `16g`、虚拟机只给了 8G，实际拿到的还是 8G。表现不是报错，而是服务器在加载模组的中途直接死掉。云服务器上同理，买了 8G 的机器，把 `-Xmx` 写成 16g 没有任何意义。

先在系统里确认真实可用内存，再决定 JVM 上限。开服前跑一次 `docker info --format "{{.MemTotal}}"`，或者直接看实例规格，两个数字对不上时以小的那个为准。

## 关服和备份：这两件事没做对，前面都白搭

PZ 服务端不响应 SIGTERM。如果你把 JVM 直接当成 PID 1，`docker stop` 会一直等到宽限期结束然后 SIGKILL，结果是 exit code 137，世界存档写到一半被杀，每一次关服都发生一次。

正确做法是用入口脚本把停止信号翻译成 RCON 的 `quit` 命令，让服务器自己走完存档流程再退出。自己搭服务端的话，关服就走 RCON，别直接 kill 进程；用别人做好的镜像，先确认它的入口脚本有没有处理这一步。

备份的默认节奏是一小时一次，本地保留 24 份，正好滚动一天。归档命名是 UTC 的 basic-ISO 格式，例如 `pzsave_20260819T230000Z.tar.gz`，好处是字典序和时间序一致，轮转旧备份和清理远端都能直接按排序切片处理，不用解析日期。

本地备份和服务器在同一块盘上，能防的是模组更新炸档和人为误删，防不了硬盘坏掉。异地备份在多数方案里默认关闭，需要自己开，推到对象存储、网盘或另一台机器上。开一个几十人的社区服，这一项别省。

## 模组：别信创意工坊的描述，只信 mod.info

服务端配置文件里有两行决定模组：`Mods` 填模组 ID，`WorkshopItems` 填创意工坊 ID，分号分隔，顺序是有意义的，装的时候别打乱。

问题出在 ID 的来源。有个实际案例：一个 287 个模组的合集，靠抓创意工坊描述页解析，其中 6 个模组根本拿不到 ID，33 个声明了多个 ID 而分不清哪个是必需项、哪个是可选依赖。创意工坊页面的描述是作者手写的，格式随意，解析出来的 ID 表经常是错的。下载到本地之后的 `mod.info` 才是权威来源，批量装模组时以它为准。

规模上要有心理准备。一个 32 槽的重模组服，服务端挂了 236 个模组（对应 220 个 Workshop 项），客户端光是订阅就要下约 9G。这种服对客户端也有要求，那家服写明需要 Build 42.21、仅支持 Windows，最低 6 核 CPU、16G 内存、8G 显存、SSD。这些是客户端配置要求，不能拿来当服务器配置推荐，但它说明一件事：模组规模上去之后，玩家和服务器两边都要付出代价。

## 现在该开哪个版本

主流已经是 Build 42.22。从监测站的实际抓取看，榜单上绝大多数服务器标的是 B42.22，个别还停在 B42.21，更老的 B41.78.19 只剩零星几个。

服务端和客户端的 build 必须匹配，玩家连不上时先查版本，再查端口。装了模组包的服还要注意模组可能锁死某个 build：前面提到的那家 32 槽模组服，页面到现在还写着要求 Build 42.21，而主流已经推到 42.22，单服页面的版本信息本来就容易滞后。需要跑 beta 分支时，服务端用 `PZ_STEAM_BRANCH` 指定分支，不要手动改文件。

如果你打算开社区服而不是朋友联机，还得接受一个运营习惯：定期清档开新赛季。监测站上 10 月下旬到 11 月初，几乎每隔几天就有一批服务器 wipe。开服前想好 wipe 节奏，比事后在群里解释为什么存档没了要省事得多。

另外提一句规模参照。公开榜单头部常见 100 到 254 槽的服，32 槽的模组服也很普遍。某监测站在一次抓取时记录了 8,317 名在线生存者、10,214 个收录服务器，其中 3,824 个当时有人在线、5,274 个带模组。这只是一个监测站的即时快照，不是官方统计，不同监测站的采样时点和口径也不一样，不能相加，但能说明带模组的服占了多数。

## 按人数选，别按价格选

**10 人以内，朋友联机，少量模组**：8G 内存、公网 IPv4、能放行 16261 加 16262-16272 一段 UDP 的机器就够。别为了省一点钱选需要逐条配 NAT 映射的实例，十几条规则的维护成本比差价高。
